02 — The business problem

A price is compared in seconds

Forum Sport is a Spanish sports retailer. Online, its price sits one tab away from every rival selling the same shoe. The question is not whether shoppers compare — it is whether Forum Sport knows what they will find.

Read the bottom row before anything else. Tradeinn is not 62% cheaper on the same shoe in the same condition — a number that extreme is a question, not an answer. It is a marketplace clearing old stock, and it is telling you that your comparison is only as good as your matching. You will spend more of week 3 on matching products than on fetching them.

Week 01 — Kick-off

Publish a page today

By tonight there is a web address, on the real internet, with your team name on it — and you got there by typing English.

Before you start

  • A GitHub account — free, use your IE email
  • A Vercel account — sign up with GitHub, not with email
  • A Supabase account — sign up with GitHub
  • Claude Code installed
  • A folder on your Desktop called forum-sport-<team>
  • Nothing else. No Python, no database software

What you do

  1. Create the three accounts.
  2. Open the assistant and point it at your folder.
  3. Ask it for a one-page site that says Hello Forum Sport.
  4. Put the folder on GitHub.
  5. Connect GitHub to Vercel and publish.

How

Open the assistant

It asks which folder to work in. Choose Desktop → forum-sport-<team> → Open. You now have one text box at the bottom of the screen. That box is the whole interface. You type sentences into it. It is not a terminal, and nothing it suggests runs until you click Yes.

Put it on GitHub

Paste the second prompt below. It will ask permission before each command: read the line, then click Yes. A browser window opens for GitHub — click Authorize.

Publish

vercel.com → Add New → Project → import the repository you just created → Deploy. About forty seconds. Vercel shows a URL ending .vercel.app. Open it on your phone. That is your page, on the internet.

Copy this prompt — 1 of 2
I am a marketing student and I do not write code. In this folder, create a single file called index.html: one page, no build step, no frameworks, nothing to install. It should show the team name "Team <NAME>" as a large heading, the line "Dynamic pricing lab — Forum Sport" under it, and today's date. White background, dark navy text, one sans-serif font, everything in a centred column no wider than 760px.

Then explain to me in three sentences, with no technical words, what the file you just made actually is and how a browser turns it into what I see.
Copy this prompt — 2 of 2
Publish this folder, step by step, and stop before each step to tell me what you are about to do.

1) Create a private GitHub repository called forum-sport-<TEAM> and push this folder into it.
2) Tell me in one sentence each what "commit" and "push" mean, as if I had never heard either word.
3) Then tell me exactly what to click on vercel.com to connect that repository and publish it — I will do that part myself in the browser.

Week 02 — Data

Turn the Excel into a database

The client's spreadsheet — 24,109 rows — stops being a file on your laptop and becomes a database your web page can ask questions of.

Before you start

  • A Supabase project, region in Europe
  • The database password saved somewhere you will find it again
  • The client's Excel saved into the folder, untouched
  • The Supabase MCP server connected to the assistant
  • You can find Project Settings → API and name the two keys

What you do

  1. Create the Supabase project and find its two keys.
  2. Plug the assistant into Supabase.
  3. Make it read the Excel and tell you what is in it — before loading anything.
  4. Load the data, and check it against totals you already know.
  5. Build a catalogue page that reads live from the database.

How

Create the project

supabase.com → New project → name it forum-sport → region Frankfurt → set a password → Create. Two minutes. Then Project Settings → API: copy the Project URL and both keys into your notes, labelled.

Plug it in

In the assistant type /mcp → Add server → Supabase → paste your project reference and a personal access token. It reports Connected. From now on you can ask "how many models are there?" and it asks the database itself instead of guessing.

Read before loading

This is the week's real lesson. In the reference build the two boring tabs of the workbook — a field dictionary and a pivot table — turned out to be the most valuable: one explained the business grain, the other became the test that proved the load was correct.

Copy this prompt — 1 of 3 · profile before you load
Before we load anything, read the Excel file in dataset/ and profile it. For every column tell me: how many values are empty, how many distinct values there are, the type, and the three most common values.

Then answer in plain language:
1) Is one row one product, or one product-in-one-size?
2) Which columns are identical for every row of the same model, and which change per size?
3) Which columns are secretly yes/no questions written as words?
4) Which columns use a word or a strange number to mean "missing"?

Do not change the file and do not create any tables yet. Give me a short table plus five sentences I could read out to the client.
Copy this prompt — 2 of 3 · load, and prove it loaded
Now design the database in Supabase: three tables — models, skus, brands. One row per model in models, one row per size in skus.

Before loading, write down the totals we expect: 1,483 models, 24,109 SKUs, 28 brands. After loading, run the counts and show me expected against actual, side by side. If any number disagrees, stop and tell me — do not fix it quietly.

Any column that is calculated from other columns, such as the net price, must be calculated by the database, not imported, so it can never drift.

Use the Supabase connection, explain each step before running it, and never write my service_role key into a file that goes to GitHub.
Copy this prompt — 3 of 3 · the catalogue page
Add a second page: the catalogue. It reads live from Supabase using the publishable key and shows one row per model — image, brand, model name, list price, sale price, discount %, stock level.

Add a search box and a brand filter. 1,483 rows is too many for one screen, so paginate at 50 with a "rows per page" control, and make the column headers sortable by clicking.

Keep it plain: white background, hairline grey rules, no colour except on the discount.

When you are done, tell me which key you used and why it is safe for that key to be visible in a public page.

Week 03 — Competitors

Read your rivals' prices

Your database stops being about you — by the end of the session it holds what other shops charge for the same shoe, today.

Before you start

  • Three competitors chosen, written down with the date
  • Their robots.txt read by you, by hand
  • An honest user agent agreed with your tutor
  • A GitHub Actions schedule you can switch on

What you do

  1. Read three competitors' rules and record what they say.
  2. Fetch one product page and find the price in it, by eye.
  3. Match their product to yours — barcode first, article code second.
  4. Store every observation; never overwrite a price.
  5. Set the two rhythms: discover weekly, refresh daily.

How

Read the rules

Type the shop's address and add /robots.txt. It is a plain text file, published to be read. Disallow: / means do not crawl — but read who it applies to. Write down what you found, and the date you found it.

Find the price by eye

Open any competitor product page. Right-click → View page source → Ctrl+F for gtin13. The block inside <script type="application/ld+json"> holds the price and the barcode, published by the shop deliberately so Google can read it. You are not breaking in; you are reading the label.

Policy is not infrastructure

What a site says and what its servers do disagree in both directions. In the reference build, adidas's robots.txt allows product pages while its firewall refuses them. Check the two separately.

Copy this prompt — 1 of 3 · fetch one page, politely
Pick one product page from a competitor and fetch it once: with an honest user agent that identifies us as a student project, obeying robots.txt, one request at a time, with a two-second wait. Do not use a headless browser and do not pretend to be a person.

From the page extract: product name, brand, barcode (gtin13), manufacturer code (mpn), price, currency, in stock yes/no.

Show me the raw block of structured data you took it from, then the clean result as a small table. Then tell me in two sentences why that data is sitting in the page at all.
Copy this prompt — 2 of 3 · the one that decides the week
Now match their products to ours, with two keys, in this order.

First the barcode: our EANs are stored as a mix of 12-digit and 13-digit numbers and competitors publish 13 digits, so pad ours to 13 with a leading zero before comparing — and tell me how many of our EANs are 12 digits, because if we skip this we lose most of our matches.

Second, when there is no barcode, the supplier article code, matched at model level: accept a match when their code equals ours, OR when the part of their code before the first hyphen equals ours — Nike publishes FQ7262-103 against our CD4371-style codes, Saucony publishes S29101-01 exactly as we store it.

Store each observed price as a new row with a timestamp. Never update a price in place: a recommendation has to be traceable back to the observation behind it.

Then report how many of our 1,483 models now have at least one competitor price, split by whether the match came from a barcode or from a code.
Copy this prompt — 3 of 3 · two rhythms
Split the crawl in two.

A weekly "discover" job that walks the competitor's sitemap, keeps only URLs that could be a running or trail shoe of a brand we stock, fetches them, and records which ones matched our catalogue.

A daily "refresh" job that re-fetches only the pages that already matched.

Log every run: pages fetched, offers found, matches made, errors, and the smallest gap we actually left between two requests, so our politeness is provable afterwards and not merely claimed.

If a fetch fails, record the failure. Never let "the request failed" and "this page had no price" end up looking like the same result.

Changing your user agent will not fix this

We tested it. One Cloudflare site refuses an honest crawler and a browser-looking one, from the same computer. Cloudflare is not reading the name you send — it is reading the shape of the connection itself, which a simple program cannot fake. Going further is a legal and commercial decision, not a technical one. It stops here.

A shop looks dead. Before you write that down: in the reference build, one site declared dead on 300 pages produced 16 matches in 10 when sampled across the sitemap instead of from the top, and six of fourteen "unscrapable" sellers turned out to be bugs in our own code. A negative result needs as much evidence as a positive one.

Your tool looks fine but the prices are a week old. Nothing on screen says so. Build the freshness display before you need it.

Week 04 — The engine

Turn prices into a recommendation

One number per product, with a sentence explaining why, and an honest score saying how much to trust it.

Read this before you build anything

There is no sales data. No units sold, no traffic, no conversion. Without demand there is no elasticity, and without elasticity there is no optimum — anyone who offers you one is selling you something. What the data does support is a rule-based recommender: a target position against a reference competitor, adjusted for stock, held inside a floor and a ceiling the client's own policy fixes. That sentence is the intellectual centre of this course.

Before you start

  • At least three competitors returning prices
  • The client's price-band matrix to hand
  • You can say what rotation classes AA, A, B, C and D mean
  • You accept that "optimal" is not on the table

What you do

  1. Pick the reference: the cheapest rival, the mean, or the median.
  2. Set a target position per rotation class.
  3. Adjust it for stock, outlet and old season.
  4. Clamp it inside the client's band matrix — and decide who wins when floor and ceiling collide.
  5. Score the data quality, separately from the price.

The four rules, in words

Target by rotation

Bestsellers set the price perception, so they sit closest to the rival. AA 100% of the reference, A 102, B 105, C 108, D 112, unclassified 106. Measured today Forum Sport sits at AA 109.8 · A 106.8 · B 109.9 · C 110.5 · D 115.0 — so every target is a cut, and the deepest cut falls on the most visible products.

Adjust for stock

Discounting what you barely have left is giving away margin. Very high stock −4 points, high −2, medium 0, low +2, very low +4.

Adjust for context

Outlet −3 points. Previous season −3 points.

The barriers

Five price bands. Each demands a minimum margin in per cent and in euros — both, not whichever is convenient — and sets a maximum alignment against the reference. The two floors are not redundant: the euro floor is the binding one on 212 models, and on 64 of the 79 in the top band. When floor and ceiling contradict each other — on 495 of 1,483 models — margin wins, and the row says so out loud.

Fig. 08 — The client's band matrix, editable on screen. Every value here is theirs, not ours.

Copy this prompt — 1 of 3 · the engine
Build the pricing recommender. It is not an optimiser: we have no units sold, no traffic and no conversion, so an economic optimum is not computable, and the page must say that in plain words.

1) Reference price = the cheapest observed competitor price for that model, switchable to the mean or the median of rivals.
2) Target position as a % of that reference, by rotation class: AA 100, A 102, B 105, C 108, D 112, unclassified 106.
3) Adjust in percentage points by stock — very high −4, high −2, medium 0, low +2, very low +4 — then outlet −3 and previous season −3.
4) Clamp with the client's band matrix, choosing the band from the CURRENT SELLING PRICE, not the list price, with bands [0,30), [30,60), [60,100), [100,200), [200,∞): minimum margins of 30/27/24/20/18 % AND 2/8/14/20/36 €, both of which must hold, and maximum alignment against the reference of 102/101/100/99/98 %.
5) Round to the nearest euro, and never let rounding break a barrier.

When the margin floor and the alignment ceiling contradict each other, margin wins — and the row must say in words that it did. Every recommendation carries a one-line reason a buyer could read aloud.

Finally, tell me how many models end up in that contradiction.
Copy this prompt — 2 of 3 · confidence
Add a confidence score from 0 to 100 to every recommendation. It measures the quality of the market data, not how sure we are about the price — put that sentence on the page where nobody can miss it.

Build it from:
- how many rivals we have a price from: 0 → 0 points, 1 → 15, 2 → 26, 3–4 → 34, 5 or more → 40
- how we matched: exact barcode 15, supplier code 8
- how fresh it is: today 20, within a week 14, within two weeks 8, within a month 3, older 0
- how much the rivals disagree: spread under 5% → 15, under 15% → 10, under 30% → 5, more → 0
- whether we know the rotation class: digital 10, store 5, neither 0

Then cap it: with a single rival the score can never exceed 45, with none it can never exceed 25. One observation cannot corroborate itself.

Under each score, list in plain words the reasons it lost points: "only one competitor", "matched by code, not barcode", "last seen 11 days ago", "rivals disagree by 22%".
Copy this prompt — 3 of 3 · make it arguable
Make every parameter editable on the page — each rotation target, each stock adjustment, and the whole band matrix — and recalculate everything the instant a value changes, with no reload. Show the default next to each control and give me a Reset button.

Then add a sanity panel at the top: how many models move down, how many move up, the average move in each direction, how many are already on target, and how many of the twenty largest moves rest on weak evidence — a single competitor, or confidence under 50%.

If a big move rests on one observation, say so right next to it rather than in a footnote.

Fig. 09 — What the hundred points are made of. The score grades the data, never the price.

Fig. 10 — Every row carries its reason. "Band 4's minimum margin leaves no room to align with the reference."

Someone asks "is this the optimal price?". The answer is no — it is the defensible price. Optimal needs demand data that does not exist.

A product changes band when it goes on sale, because the band follows today's selling price, not the list price. That is deliberate. Say it before someone discovers it.

→ You leave with a recommended price, and a reason, per model

Week 05 — Brand

Make it look like the client

Same numbers, different owner. By the end the tool looks like it was made inside Forum Sport, and it works for someone reading it on a phone in a stockroom.

Before you start

  • The client's site open in a browser tab
  • Their logo, in a vector file if you can get one
  • Six values written down — and only six
  • A phone to test on, not just a narrow window

What you do

  1. Harvest the brand from the client's own site.
  2. Write it down once, as a set of named values.
  3. Apply it everywhere at once.
  4. Fix the two things that always break: the table on a phone, and colour used as the only signal.
  5. Add Spanish/English and light/dark.

How

Harvest

Open the client's site. Right-click anything → Inspect. The Styles panel shows the exact colour and the font name. Write down six values and no more: brand colour, text colour, hairline grey, background tint, font family, corner radius. Six is a design system; sixty is a mood board.

Name them once

Put the six at the top of the file as named values and rewrite every rule to use the names. After that, changing the brand is changing six lines — which is exactly what makes dark mode possible in the next step.

Copy this prompt — 1 of 3 · name the brand
Here are six values I took from the client's own site: brand colour <#>, text colour <#>, hairline grey <#>, background tint <#>, font family <name>, corner radius <n>px.

Put them at the top of the file as named variables, add a spacing scale and three type sizes, then rewrite every rule in the page to use those names — no colour written directly anywhere.

When you are done, list every colour still hard-coded somewhere, because those are the ones that will go wrong later.
Copy this prompt — 2 of 3 · the two things that always break
Two fixes.

First: this table has thirteen columns and is unreadable on a phone. Below 760px wide, drop the least load-bearing columns rather than squeezing them, and make sure no price is ever cut off — a price shown as "180,0…" reads as a different number. Check every cell, not just the headers.

Second: we are signalling "cheaper" and "dearer" with colour alone. Add a sign (+ / −) and a word, so it still reads in greyscale and for a colour-blind buyer.

Then check every text colour against its background and tell me which pairs fail WCAG AA contrast, with corrected values.
Copy this prompt — 3 of 3 · two languages, two themes
Add a Spanish/English switch. Pull every visible piece of text into a single dictionary at the top of the file, one entry per key with both languages side by side, so a non-technical person can change the wording without touching any logic.

Rebuild the number and date formatters when the language changes: "1.483" and "1,483" are the same number, and the thousands separator is part of the translation, not decoration around it.

Then add light/dark, following the system setting by default. Dark is not inverted light: give me a separate set of values for the same named variables and keep the same contrast ratios.

Finally, list any key that exists in one language and not the other.

Fig. 11 — The same build in Spanish and dark (left) and on a 390px phone (right). Same values, renamed.

Dark mode makes the accent unreadable. Change the value, not the component — that is what naming them was for.

A missing translation fails silently and shows English. Ask for the list of missing keys, every time.

→ You leave with a tool that looks like the client's
